# i18n Multilingual Support (ES / PT / EN)

## Overview

This specification suite adds full multilingual support (Spanish, Portuguese, English) to Biblio Checker — covering the frontend UI **and** the natural-language text generated by the worker (`decisionReason`, `warnings[].message`). Users pick their language with a header toggle; that choice drives the UI strings *and* travels with every `POST /api/analysis/start` request so that the worker renders results in the same language.

## Problem Statement

1. **Language mixed at random.** The frontend currently mixes hardcoded Spanish (`"Texto original"`, `"Razon de la decision"`, `"Verificada"`) with hardcoded English (`"Recent Analyses"`, `"Queued"`, `"Upload Your Bibliography"`). `<html lang="en">` is hardcoded regardless of content.
2. **No i18n library installed.** No `next-intl`, `next-i18next`, `i18next`, or any locale routing. ~75+ user-facing strings are inline JSX.
3. **Worker generates Spanish-only text.** `classification.py` has 11 deterministic rules that produce `decisionReason` strings like `f"El DOI {doi} coincide con '{title}' ({year}) en {source}."`. Nodes under `apps/worker/biblio_checker_worker/langgraph/nodes/` emit warnings in Spanish (`"La fuente X no respondió..."`, `"El documento no contiene texto extraíble."`). Even with a translated UI, the result payload would still show Spanish text.
4. **ResultsV1 contract hardcodes Spanish.** `apps/backend/app/schemas/results.py` declares `reportLanguage: str = Field(..., pattern=r"^es$")` — the schema literally forbids other languages.
5. **No locale carried end-to-end.** The `analysis_jobs` table has no `locale` column; the worker has no way to know which language to render text in.

## Scope

**In scope:**
- Add `locale` column to `analysis_jobs` (enum: `es | pt | en`, default `es`).
- Extend `POST /api/analysis/start` contract to accept `locale`; persist and pass to the worker via `claim_analysis_job`.
- Create a worker-side i18n catalog (`langgraph/i18n.py`) with `render(key, locale, **params)` and populate ES/PT/EN templates for all 11 classification reasons and all worker warnings.
- Thread `locale` through `GraphState` and every node/function that currently builds Spanish strings.
- Widen `ResultsV1.reportLanguage` pattern to `^(es|pt|en)$` in both the Pydantic (backend) and Zod (frontend) schemas.
- Install `next-intl` on the frontend (no-routing mode), register locale detection (Accept-Language + localStorage), and provide ES/PT/EN message catalogs covering every hardcoded string.
- Migrate all frontend components that render user-facing strings to `useTranslations()` / `getTranslations()`.
- Add a `LanguageToggle` in the header (next to `ThemeToggle`); wire locale into the `analysis-start-gateway` route.
- Translate HTTP error responses returned by backend controllers using `Accept-Language`.
- Test coverage across all three languages: worker templates, backend contract, frontend component snapshots, end-to-end manual QA.

**Out of scope:**
- Translating `rawText` (the bibliographic reference extracted from the user's document — it is user-provided content).
- URL-based locale routing (`/es/...`, `/pt/...`). Left for a future SEO-focused iteration.
- Re-translating already-completed analyses when the user changes language. `locale` is fixed at job creation time.
- RTL languages — not needed for ES/PT/EN.
- Translation of LLM-generated free text beyond what already exists (e.g., no LLM is invoked to re-translate reasons).
- Backend **audit log** messages or **structured logs** — those stay in English (operator-facing).

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Locale per analysis (immutable) | Stored on `analysis_jobs.locale` at creation | Simpler than post-hoc re-translation; the worker renders once in the chosen language. |
| Where translation happens for `decisionReason` / `warnings[].message` | **Worker-side templates** (not frontend codes) | User chose this approach (see plan). Avoids refactoring 11 classification rules into structured codes + params. |
| Frontend i18n library | `next-intl` | Most idiomatic for the Next.js App Router; supports both routing and no-routing modes. |
| Locale routing | **No URL prefix** | Matches user's request; simpler UX; no migration of existing links. |
| Locale detection order | `localStorage` → `Accept-Language` → default `es` | `localStorage` preserves explicit user choice; `Accept-Language` is the first-visit heuristic. |
| Default language | `es` | Current content is predominantly Spanish; least-surprise for existing users. |
| Enum-like result fields (`classification`, `confidenceBand`, `reasonCode`, `matchType`) | Translated **on frontend only** via message catalogs | They are already codes in the contract; no backend work needed. |
| Backend HTTP error messages | Translated using `Accept-Language` header | They are emitted before a job exists (auth errors, service-unavailable), so the job's `locale` is not available. |
| `ResultsV1.reportLanguage` | Widened from `^es$` to `^(es\|pt\|en)$` | Current schema forbids other values; must be relaxed and echoed by the worker. |
| Missing translation key at runtime | Fallback to `es` + log a warning (`i18n_missing_key`) | ES is the most complete source-of-truth; noisy fallback surfaces gaps without breaking UX. |
| Interpolation syntax | ICU-style `{name}` placeholders | Both `next-intl` and Python `.format()` support this natively. |

## Feature Summary

| Component | Change |
|-----------|--------|
| DB | New column `analysis_jobs.locale` + CHECK constraint + migration of RPC `claim_analysis_job`. |
| Backend contract | New optional `locale` field in start request; persisted; returned when claiming jobs. |
| Backend errors | ~6 HTTP error messages translated via `Accept-Language`. |
| Worker | New `langgraph/i18n.py` with ~25 keys × 3 locales = ~75 templates. |
| Worker nodes | `classify.py`, `verify.py`, `parse_references.py`, `normalize.py`, `cross_patterns.py` use `render(...)` instead of f-strings for user-facing messages. |
| Worker classification | 11 rules in `classification.py` refactored to use the i18n catalog. |
| Results contract | `reportLanguage` widened to `^(es\|pt\|en)$` (Pydantic + Zod). |
| Frontend infra | `next-intl` installed, plugin wired, `LocaleProvider`, dynamic `<html lang>`, locale detection. |
| Frontend catalogs | `messages/es.json`, `messages/pt.json`, `messages/en.json` (~75 keys each). |
| Frontend components | ~10 files migrated to `useTranslations()`. |
| Frontend UX | `LanguageToggle` added; locale sent with analysis-start request. |
| Tests | Worker i18n unit tests; backend contract tests; frontend render tests; manual E2E checklist. |
