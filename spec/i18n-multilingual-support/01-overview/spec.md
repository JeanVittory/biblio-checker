# Step 01 — Overview: Locale Model, Detection, and Translation Boundaries

## Scope

- Define the set of supported locales and their canonical codes.
- Define the locale-detection order and persistence.
- Define the translation boundaries: which subsystem renders which strings.
- Define the interpolation / placeholder syntax used across the stack.
- Define the fallback strategy when a translation key is missing.

**Out of scope:** Database changes (Step 02). API contract changes (Step 03). Concrete translations (Steps 06, 07, 09).

## Context

Biblio Checker has three user-facing text surfaces:

1. **Frontend UI chrome** — buttons, labels, headings, status badges, error toasts (~75 strings).
2. **Backend HTTP error responses** — e.g. `"Invalid or expired token"` from `apps/backend/app/api/controllers/analysis/status.py`.
3. **Result payload free text** — `references[].decisionReason` and `warnings[].message` generated by the worker (currently Spanish-only).

Each surface needs a clear rule for *who* renders it and *how* the language is chosen. This step establishes those rules so that every subsequent spec refers back to a consistent model.

## Requirements

### 1. Supported Locales

The platform supports exactly three locales, identified by ISO 639-1 codes:

| Code | Language | Native name | Default in UI |
|------|----------|-------------|---------------|
| `es` | Spanish | Español | **yes** (default fallback) |
| `pt` | Portuguese | Português | — |
| `en` | English | English | — |

Additional codes (e.g. `es-ES`, `pt-BR`, `en-US`) **must** be normalised to the base two-letter code. Unknown codes **must** fall back to `es`.

**Locale constant (frontend — `apps/frontend/i18n/config.ts`):**

```typescript
export const LOCALES = ["es", "pt", "en"] as const;
export type Locale = (typeof LOCALES)[number];
export const DEFAULT_LOCALE: Locale = "es";

export function normalizeLocale(input: string | null | undefined): Locale {
  if (!input) return DEFAULT_LOCALE;
  const base = input.toLowerCase().split("-")[0];
  return (LOCALES as readonly string[]).includes(base) ? (base as Locale) : DEFAULT_LOCALE;
}
```

**Locale constant (worker — `apps/worker/biblio_checker_worker/langgraph/i18n.py`, detailed in Step 05):**

```python
from typing import Literal

Locale = Literal["es", "pt", "en"]
LOCALES: tuple[Locale, ...] = ("es", "pt", "en")
DEFAULT_LOCALE: Locale = "es"
```

**Locale constant (backend — `apps/backend/app/schemas/common.py` or equivalent):**

```python
from typing import Literal
Locale = Literal["es", "pt", "en"]
```

### 2. Locale Detection Order

The frontend resolves the active locale using this priority:

```
1. localStorage.getItem("locale")           # explicit user choice from LanguageToggle
2. Cookie "NEXT_LOCALE" (set alongside localStorage for SSR)
3. Accept-Language header                    # first-visit heuristic
4. DEFAULT_LOCALE ("es")                     # ultimate fallback
```

- `localStorage` and the cookie are kept in sync by the `LanguageToggle` (Step 11). They must be written together.
- `Accept-Language` parsing must pick the **highest-weighted** tag whose base code is in `LOCALES`. Implementation uses a small helper in `apps/frontend/i18n/detect.ts`.
- Server Components read the locale via `cookies()` and `headers()` from `next/headers`.

### 3. Translation Boundaries

| Surface | Source of truth | Language source |
|---------|-----------------|-----------------|
| Frontend UI chrome | `apps/frontend/messages/<locale>.json` | Active frontend locale (Section 2) |
| Enum labels in results (`classification`, `confidenceBand`, `reasonCode`, `matchType`) | Frontend message catalog under `results.*` | Active frontend locale — the backend emits codes, the frontend labels them |
| `references[].rawText` | User-provided content | **Not translated** — displayed verbatim |
| `references[].normalized.*` | Extracted metadata | **Not translated** — displayed verbatim |
| `references[].decisionReason` | Worker (`classification.py`) | Job's stored `locale` — rendered at pipeline execution time |
| `warnings[].message` | Worker (`nodes/*.py`, `classification.py`) | Job's stored `locale` — rendered at pipeline execution time |
| Backend HTTP error responses | Backend controllers | `Accept-Language` header of the request (no job context available) |

### 4. ICU-Style Interpolation Syntax

All translation strings use single-brace ICU-lite placeholders:

- **Frontend (`next-intl`):** natively supports `{name}`, `{count, plural, ...}`, `{date, date, ...}`.
- **Worker (`str.format_map`):** supports `{name}` positional substitution. Complex plural/date formatting is **not required** in the worker templates; numbers and names are pre-formatted by callers (e.g. `_score_pct(score)` already returns `"85%"`).

Example:

```
# Spanish
"doi_match.single": "El DOI {doi} coincide con '{title}' ({year}) en {source}."

# Portuguese
"doi_match.single": "O DOI {doi} corresponde a '{title}' ({year}) em {source}."

# English
"doi_match.single": "DOI {doi} matches '{title}' ({year}) in {source}."
```

### 5. Fallback Strategy for Missing Keys

| Layer | Behaviour when key is missing in the active locale |
|-------|-----------------------------------------------------|
| Worker `render(key, locale, ...)` | Fall back to `DEFAULT_LOCALE` (`es`). If still missing, return `f"[i18n:{key}]"` and emit a **worker warning** `{"code": "i18n_missing_key", ...}` (warning system already exists). |
| Frontend `useTranslations` | Fall back to `DEFAULT_LOCALE`. If still missing, log a client-side `console.warn` and render the key itself in dev; render empty string in prod. Configured via `NextIntlClientProvider`'s `onError` handler. |
| Backend error helper | Fall back to English constant if neither the requested locale nor the default is available for the error code. |

**No UX-breaking exceptions are allowed.** A missing key must never throw or render a placeholder like `undefined`.

### 6. Locale Immutability per Analysis

Once a job is created with a given `locale`, every field rendered by the worker uses that locale. Changing the UI language after the job has been created **must not** re-render backend text — `references[].decisionReason` reflects the language the user requested at submission time. This keeps storage, audit logs, and UI consistent and avoids re-processing.

The frontend UI chrome around a historical job (badges, table headers) **does** switch with the live UI locale. Only the free text embedded in the result payload is locked.

### 7. Naming Conventions for Translation Keys

Namespaced, dot-separated, lowercase-with-underscores:

- **Frontend:** `common.submit`, `upload.drop_here`, `recent.table.actions`, `status.queued`, `results.classification.verified`, `errors.file_too_large`.
- **Worker:** `class.doi_match.single`, `class.doi_match.multi`, `class.doi_conflict.title_known`, `warn.source_timeout`, `warn.empty_document`, `warn.invalid_doi_format`.

Namespace prefixes used throughout the suite:

| Prefix | Owner | Covers |
|--------|-------|--------|
| `common.*` | frontend | generic UI affordances (Submit, Cancel, Close, Copy) |
| `upload.*` | frontend | upload flow, dropzone, progress |
| `dropzone.*` | frontend | drag-and-drop specific |
| `recent.*` | frontend | recent analyses table + rows |
| `status.*` | frontend | status badges (queued, running, succeeded, failed, expired) |
| `results.classification.*` | frontend | enum labels for `classification` values |
| `results.confidence_band.*` | frontend | labels for `confidenceBand` values |
| `results.reason_code.*` | frontend | tooltip labels for `reasonCode` |
| `results.match_type.*` | frontend | evidence `matchType` labels |
| `results.fields.*` | frontend | normalized field labels (Authors, Year, ISSN, ...) |
| `results.sections.*` | frontend | section headers inside ExpandedDetail |
| `errors.*` | frontend | toast/inline error text |
| `class.*` | worker | classification reasons |
| `warn.*` | worker | warning messages |

## Acceptance Criteria

- [ ] `LOCALES = ("es", "pt", "en")` with `DEFAULT_LOCALE = "es"` is defined identically on the three sides (frontend TS, worker Python, backend Python).
- [ ] `normalizeLocale()` utility exists on the frontend and strips region suffixes (`es-ES` → `es`, `zh-CN` → `es` via fallback).
- [ ] Detection order is documented and implemented as `localStorage → cookie → Accept-Language → default`.
- [ ] Translation boundary matrix (Section 3) is honoured — no worker template is rendered on the frontend and no frontend catalog string leaks into the worker.
- [ ] Placeholder syntax is exclusively `{name}`; no `%s`, no f-string concatenation in templates.
- [ ] Missing-key fallback chain behaves as described in Section 5.
- [ ] Locale is stored per analysis and is immutable after creation (Step 02 enforces the DB side).
- [ ] Key namespacing matches Section 7.
